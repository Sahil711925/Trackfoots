The Big Hack 2.0 · Track 02 · Problem B3

Evidence the attacker can't delete.

Your security logs sit on the machine the attacker just took over. Trackfoots chains every line, seals each batch into a Merkle root, and writes that root to a contract that refuses to overwrite it. Delete the logs — the proof they existed is already somewhere else.

01 How it works

Sixteen lines, four hashes, one root.

Read it bottom to top. Every entry is hashed once as a leaf, then paired upward until a single 32-byte root remains. That root is the only thing that goes on-chain — and the only thing an attacker cannot touch.

one entry's proof path — 4 hashes, not 16 deleted after sealing — the root still commits to it present leaf
STAGE 01

Entries arrive

Over the API or through the shipper. Each line gets a sequence number at write time.

STAGE 02

Leaf hash

SHA-256 with a 0x00 prefix, so a leaf can never be mistaken for an interior node.

STAGE 03

Pair upward

Neighbours combine with a 0x01 prefix: 16 → 8 → 4 → 2. Any edit changes every parent.

STAGE 04

Root

One 32-byte value commits to all sixteen lines, including the two that were deleted.

STAGE 05

Anchor

anchor(seq, root, org) — write-once. A published root can never be changed again.

02 What an auditor sees

A verifier that doesn't trust us.

Export a bundle and it verifies offline — no access to our log files, no account, no phone call. Every receipt is checked, and the set is checked for completeness against its own Merkle root.

05 Threat model

What it catches, and what it can't tell you.

Nine attacker capabilities, judged one at a time. This is the table an auditor actually wants, and it is the reason the product is credible: the gaps are listed next to the wins.

Attacker capabilityDetected?What catches itWhat it can't tell you
Delete log linesYesPublished root no longer matches the recomputed leaf countWhich content was in the deleted lines
Edit a lineYesHash chain breaks at that entryWho edited it
Reorder linesYesSequence numbers are inside the digest—
Rewrite every hashYesOnly the anchored root — local checks pass by designContent, still
Truncate the tailYesFewer entries than the last published checkpointLines after the last anchor
Replace the data dirYesEvery root diverges; receipts on disk don't matchWhen the swap happened
Backdate timestampsPartlyTimestamps are inside the digest, but an attacker who rewrites hashes can change themTrue event time
Block outbound networkPartlyLiveness check raises STALE and alertsAnything written after anchoring stopped
Steal the anchor keyNo, for new rootsOld roots stay frozen; a gap in sequence numbers is visibleWhether new roots are honest

A malicious operator with the anchor key can publish false roots going forward. That is stated in the README, not hidden — the mitigation is a second signer, which we did not build.

06 Adopting it

Three ways in, none of which touch your code.

SHIPPER

Tails an existing file

Parses sshd, nginx or syslog, resumes from a byte offset, survives rotation.

API

One POST per event

A signed receipt comes back at write time — proof before any attacker exists.

TENANTS

One process per company

Own data dir, own key, own sequence namespace. Isolation you can point at.

09 Plain answers

Including the uncomfortable ones.

What does a passing verification actually prove?

That the record you hold is the record that existed when the root was published — nothing edited, deleted or reordered. It does not prove what was written was true, or who wrote it. A deleted line's content cannot be recovered from a hash; only its existence and position can be proven.

Where is it running right now?

A local EVM, with the same contract compiled for Polygon Amoy. The Amoy deployment was attempted and blocked: the deployer holds zero testnet POL and every reachable faucet requires a captcha, a mainnet balance or a social login. The attempt, with literal error text, is in the repository.

What happens if the attacker deletes lines before the next anchor?

Anything written through the API is covered immediately — the receipt leaves the box at write time. A line written straight to disk by a process we don't control is protected only from the next anchor, and the liveness check raises an alert when anchoring stops.

The attacker owns the server. He still can't rewrite history.
