TRACKFOOTS

Tamper-evident security logs — the proof survives the attacker
THE BIG HACK 2.0 · TRACK 02 · PROBLEM B3 — LOGS THE ATTACKER CAN'T ERASE

An attacker with root access can delete a company's logs. We make the logs deletable but the proof permanent — by publishing one Merkle root per batch to a blockchain, so tampering is detectable and the deleted lines remain provable.

The problem

CERT-In requires Indian organisations to retain security logs for 180 days and report specified incidents within 6 hours. Those logs are the only record of how a breach happened and what was taken.

But the logs live on the same machine the attacker now controls. With root access he deletes the incriminating lines, and the company can no longer prove anything — to a court, an auditor, or the regulator. In the WazirX and CoinDCX cases, the losses were approved through interfaces nobody could read; in most enterprise breaches the forensic trail is destroyed the same way.

Local hashing alone does not fix this. A capable attacker edits an entry and then recomputes every hash downstream. The file becomes internally perfect and every local check passes. We built that attacker and demonstrated it.

Our approach

  • Hash chain. Every entry is hashed together with the previous entry's hash. One edit breaks every hash after it.
  • Merkle batching. Every 100 entries are reduced to a single 32-byte root, so only one small value needs to be published per batch.
  • RFC 6962 Merkle tree. The tree follows the Certificate Transparency standard — domain-separated leaves (0x00) and nodes (0x01), subtrees split at the largest power of two — and passes the standard's construction checks in our test suite rather than a hand-rolled variant.
  • Consistency proofs. Consecutive checkpoints are linked, so the log is provably append-only across time. Two internally consistent but different histories cannot both extend the same published root, which makes a fork detectable and not just tampering.
  • On-chain anchoring. The root is written to the LogAnchor smart contract. The contract refuses to overwrite an existing sequence number, so a published root can never be changed — not by the operator, not by the attacker.
  • Write-time receipts. Every application that writes a line through the ingest API gets back a signed receipt immediately — sequence, content hash, HMAC tag — held off-box by the emitter. Deleted lines can be proven to have existed even when the whole log is gone.
  • Receipt-set commitment. Individual signatures prove a receipt is real; a Merkle root over the receipt set proves you were handed all of them. An attacker who owns the receipt store cannot quietly drop one without breaking the committed root.
  • Filing, not just detecting. Detection produces a CERT-In 6-hour notification: incident ID, detection time, affected sequences, published roots, contract address, verification steps for the recipient — and an explicit section listing what the evidence cannot prove.

Why the blockchain is load-bearing

Remove the chain and the system fails its own test: the attacker holds the server, so anything stored only on the server can be rewritten. The chain supplies the one property the server cannot manufacture — an independent witness that recorded the value before the attack. Verification therefore reduces to comparing recomputed roots against roots that were published earlier and cannot move.

The attacker owns the server. He still can't silence the witness.

Who it helps

Indian SaaS companies, fintechs, banks and hospitals that must retain logs under CERT-In directions and must answer auditors and courts after an incident. India ranks first on Chainalysis's 2026 global crypto-adoption index and CERT-In handled roughly 30 lakh incidents in 2025, so incident evidence is a national-scale problem, not a niche one. CERT-In itself has moved audit-certificate verification onto a blockchain (AMBAK, July 2026) — we apply the same pattern one level down, from the certificate to the evidence behind it.

Hash chain, RFC 6962 Merkle tree with inclusion, consistency and incremental-checkpoint proofs, a Solidity contract, an authenticated ingest API, an anchoring worker, an independent auditor, two attacker profiles, a CERT-In report generator and a web UI.

Honest limitations

  • Entries written directly to disk, bypassing the ingest API, are protected only by the hash chain until the next anchor lands. Applications that write through the API get a signed receipt at write time, which closes that window for them — this is built, not planned.
  • If the attacker blocks outbound traffic, new anchors stop. History cannot be rewritten, but new entries go unwitnessed until the staleness check fires — it now raises an alert.
  • If the anchor signing key is stolen, the attacker can publish new roots — but never alter old ones.
  • Local EVM, not a public testnet. The contract compiles for Polygon Amoy, the Amoy RPC is reachable and the transaction was signed and broadcast — it was rejected for gas because we could not obtain testnet POL: every faucet available from this host requires a captcha, a mainnet balance or a social login. The attempt, with literal error text, is in docs/AMOY-ATTEMPT.md. We did not fake a transaction hash.
  • Single node. No replication, no fsync, no HA. The security properties hold; the availability properties are a deployment problem we did not solve in 24 hours.
All log data in the demonstration is synthetic. No personal data is written to the chain — only Merkle roots. The Merkle-logging primitive is established prior art (Certificate Transparency, Trillian, Sigstore Rekor); the contribution is the incident-evidence workflow and the compliance framing, not a new data structure.
